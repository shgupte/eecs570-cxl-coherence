# What a CXL pool needs for DLRM training: scheduled sharing, not reactive coherence

Campaign of 2026-11-14. Plan: `CAMPAIGN.md`. System: 8 GPUs, one CXL pool
holding the embedding tables, synchronous training, Criteo 1TB (65,536
samples per step, 26 tables, 512 B rows). Baseline: CLAY (ICS'24) extended to
training, i.e. an uncacheable pool.

## Result in one table
gem5, whole training step (lookup + gradient return + row update), uniform
1/64 sample of the rows of 12 consecutive real steps, 256-cycle CXL hop,
38 GB/s pool port. Step time in µs; "critical" = step time if rows that do
not depend on the previous update are prefetched during GPU compute.

| Design | Step | Critical | vs baseline |
|---|---|---|---|
| Uncacheable pool, a reader combines gradients (**baseline**, CLAY for training) | 108.4 | 85.6 | 1.0x |
| + affinity sample placement | 71.2 | 43.9 | 1.5x |
| + software keeps rows private to one GPU | 54.3 | 34.3 | 2.0x |
| + commutative merge at the pool instead of a combiner (**proposal**) | **48.7** | **25.7** | **2.2x (3.3x critical)** |
| MESI, CXL-style (ownership moves through the pool), affinity placement | 54.7 | 41.5 | 2.0x |
| MESI with GPU-to-GPU forwarding (not possible in CXL 3.0), affinity placement | 40.2 | 27.0 | 2.7x |
| MESI, CXL-style, default placement | 108.9 | 87.7 | 1.0x |

The same ordering holds at 8x the trace scale (831 -> 369 µs, 2.25x) and for
hop latency 128/512 cycles, port bandwidth 0.5x/4x and 128 outstanding
requests. A second window of steps (16-27 instead of 2-13) reproduces it:
108.4 -> 46.6 µs, CXL-style MESI 53.2, forwarding MESI 39.6
(`results_gem5_step_matrix.csv`, 129 runs).

## Findings
1. **The earlier hot-row study looked at about 3% of the traffic.** The top
   1,000 rows are 73% of lookups but, after per-GPU deduplication, a step
   fetches ~297K (GPU,row) pairs over ~163K unique rows. 39% of pairs are
   rows read by one GPU.
2. **A pool moves fewer bytes than sharding** (`step_traffic.py`): 1.4x fewer
   row transfers per step than deduplicated sharded all-to-all and 7.7x fewer
   than per-lookup all-to-all on Criteo; 1.5x and 7.3x on Meta's multi-hot
   batches. This is the case for the pool itself.
3. **Sample placement is free and is the largest lever.** Which GPU runs
   which sample does not change the summed gradient. Greedy sharing-aware
   placement (`sample_placement.py`) cuts row fetches 29% (297K -> 211K) and
   raises single-reader rows from 73% to 87%. Adding affinity to the previous
   step makes 30% of fetches rows that the same GPU alone updated last, so
   its copy is still current.
4. **Hardware MESI does not beat software in a CXL-realistic pool.** With
   the gradient path modeled, MESI first looked best. That lead came from
   MESI_Two_Level forwarding lines GPU to GPU without using the pool port.
   With ownership transfers routed through the pool (new `--pool-mediated`
   protocol option), MESI ties the uncacheable pool with a software cache
   (54.7 vs 54.3 µs) and loses to commutative merge (48.7). MESI with
   mailboxes is worse still (66.7). MESI wins only if the fabric allows
   peer-to-peer forwarding.
5. **Gradient return is where the protocol matters.** Combining gradients at
   a reader costs two transfers per extra reader; a commutative add at the
   pool costs one. It is 10-14% of step time and 25% of the critical path
   once placement has made most rows private.
6. **Lookahead halves the critical path.** With affinity placement only 49%
   of fetches depend on the previous step's update; the rest can be fetched
   during GPU compute.
7. **One-step-stale reads cost no measurable accuracy** (`staleness_train.py`,
   real DLRM training, 28.6M Criteo samples, global batch 65,536): AUC
   0.7346-0.7417 exact, 0.7379-0.7441 with 1-step delay, 0.7415-0.7459 with
   4-step delay (3 seeds for delay 0 and 1). If one step of staleness is
   accepted, every fetch can be prefetched and only gradient return stays on
   the critical path.

## Proposal: scheduled sharing
The data loader knows each step's read and write sets before the step runs.
Use that instead of reacting to misses:
- place samples so rows are private to one GPU where possible (scheduling);
- keep private rows in the GPU and skip both the fetch and the store until
  another GPU needs them (software-managed ownership, the useful part of MESI);
- merge gradients of shared rows with a commutative add at the pool
  (COUP-style coherence, one adder per port);
- prefetch rows that do not depend on the previous update (lookahead), or all
  rows under one-step bounded staleness (consistency).

## Limits (read before quoting numbers)
- Commutative merge is emulated (one write-back per reader), not implemented
  in the protocol, and it needs an adder at the pool (light near-memory logic).
- A kept row that needs a store is charged a load instead (same count,
  opposite direction).
- Pool-mediated MESI changes only ownership transfers (GETX); a read of a
  line another GPU owns is still forwarded, which favors MESI slightly.
- The "keep" window is 4 steps to match a 1 MiB GPU cache; a real GPU cache
  holds far more, which helps both keep and MESI.
- Placement uses a greedy heuristic on one-hot data; its run time and
  multi-hot behavior are not evaluated. GPU compute is not simulated.
- The accuracy run is short (436 steps, small model); it shows no effect, not
  equivalence at convergence.

## Novelty (honest)
Each mechanism has a precedent: Herald (NSDI'24) placement over RDMA
parameter servers; BagPipe (SOSP'23) and ScratchPipe (ISCA'22) lookahead
caches; COUP (MICRO'15) commutative coherence on multicores; ReCXL (ISCA'24)
and TrainingCXL do the whole embedding update inside CXL memory. Not found in
prior work: these evaluated together for a plain CXL pool shared by
accelerators with the whole training step, and the result that
CXL-style hardware coherence adds nothing over scheduled software ownership.

```
# placement and traffic (Criteo batches from criteo_to_batches.py)
python3 analysis/sample_placement.py --batches <batches/d1> --out <cache/pl_aff2> --policy affinity --cmax 512 --beta 2 --passes 0
python3 analysis/step_traffic.py <cache/pl_aff2>

PACK_FILE=runs.tsv CACHE=<cache dir> TRACES=<trace dir> analysis/run_step_matrix.sh

# accuracy
python3 analysis/staleness_train.py prep --day-dir <criteo day> --out d.npz
sbatch --export=ALL,DATA=d.npz,CONFIGS="0:2e-3:0 1:2e-3:0" slurm/v2/stale_train.sbatch
```
