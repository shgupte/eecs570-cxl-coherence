# CXL pool vs sharded all-to-all for DLRM training, and what the pool needs

Campaign of 2026-11-14 (plan: `CAMPAIGN.md`). System: 8 GPUs, synchronous
training, Criteo 1TB (65,536 samples per step, 26 tables, 512 B rows).
Second version: it adds the comparison with Meta-style sharded all-to-all,
an explicit port model, real update messages in the protocol, and the
placement checks. It replaces the numbers of the first version (see
"Corrections").

## Fourth version (2026-11-15): bulk transfers change the ordering (read this first)
All numbers below this section limit every GPU to 32 outstanding requests,
so each design pays the link latency once per 32 lines. Real sharded
all-to-all sends one bulk message per GPU pair. `analysis/run_port_bulk.sh`
reruns the main designs with windows 256 and 16,384 (24 runs,
`results_gem5_port_bulk.csv`; `configs/cxl-trace.py` raises the sequencer
and TBE limits when the window is above 128). The two windows agree within
4%: at 256 every design is limited by port bandwidth.

Step µs, window 32 -> bulk (16,384):

| design | window 32 | bulk |
|---|---|---|
| sharded, per lookup | 201.8 | 161.3 |
| sharded, dedup | 44.6 | 27.6 |
| sharded + placement | 33.7 | 20.3 |
| sharded + placement + row migration | 17.0 | 12.2 |
| pool 8 ports, CLAY-style baseline | 75.8 | 35.1 |
| pool 8 ports, baseline + placement | 41.4 | 19.3 |
| pool 8 ports, software (keep window 16) | 23.6 | 11.1 |
| pool 8 ports, MESI + commutative | 23.4 | 11.2 |
| pool 1 port, CLAY-style baseline | 185.0 | 169.9 |
| pool 1 port, baseline + placement | 116.3 | 112.0 |
| pool 1 port, software (keep window 16) | 75.5 | 74.7 |
| pool 1 port, MESI + commutative | 63.9 | 63.2 |

- With bulk transfers the 8-port pool is 2.5x faster than dedup sharding,
  1.8x faster than sharding with placement and 1.09x faster than sharding
  with row migration (a tie within modelling error). "Sharding with row
  migration beats the pool" (third version) holds only at window 32.
- The pool wins with more link hardware: a sharded remote row crosses two
  GPU ports, the 8-port pool adds 8 ports. Bandwidth decides, not coherence.
- One port is still not enough (63-75 µs, loses to every sharded design
  except per lookup). Software still ties hardware at 8 ports; at one port
  MESI + commutative is 18% faster.
- Mixed case: sharding bulk but the pool at window 32 gives pool 23.4 vs
  dedup 27.6, placement 20.3, migration 12.2. A window of 256 avoids it.
- Remaining bias against sharding: a 64 B request per row where a real
  system sends an 8 B index (about 10% more traffic).

## Third version: checks that change the conclusion
Full report with figures: https://claude.ai/artifact/67XjdC8skLE98faHYZS8EG
(private to its owner until shared). `results_gem5_port_checks.csv`, 40 runs.

1. **Sharding with row migration beats the pool.** If the schedule moves a
   row to a GPU that reads it when its owner does not
   (`gen_shard_traces.py --mode shard_mig`), sharded all-to-all takes 17.0 µs
   per step against 23.4 for the best pool design (8 ports) and 33.7 for
   sharding with placement only. A moved row is fetched once and never
   written back. So the pool is not faster than a well-scheduled sharded
   system; its remaining argument is capacity. At 8x trace scale: 132.7 vs
   172.0. Sensitivity: 25.1 (19 GB/s ports), 14.5 (154 GB/s), 13.2 (hop
   128), 49.7 (hop 1024); only with half-speed GPU ports does the pool tie.
2. **Second window and second day agree.** Step µs for day 1 steps 2-13 /
   day 1 steps 16-27 / day 2 (2015-03-10): per lookup 201.8 / 199.6 / 173.8;
   dedup 44.6 / 44.1 / 44.7; + placement 33.7 / 33.3 / 34.9; + migration
   17.0 / 16.1 / 18.4; pool baseline 75.8 / 74.6 / 77.4; pool software
   24.8 / 24.5 / 26.4; MESI CXL-style 28.8 / 28.2 / 30.1; MESI + commutative
   23.4 / 23.1 / 24.8.
3. **Software keep window.** The keep plan now sees the steps after the
   trace (it used to store rows it could keep). Window 4 / 8 / 16 steps:
   24.8 / 24.3 / 23.6 µs at 8 ports and 79.5 / 77.5 / 75.5 at one port,
   against 23.4 and 63.9 for MESI + commutative updates. Software ties
   hardware at 8 ports; at one port hardware stays 15-19% faster.

The sections below are the second version; where they say the pool is
1.3-1.44x faster than sharding, that holds only against sharding without
row migration.

## Result in one table
gem5, whole training step (lookup + gradient return + row update), uniform
1/64 sample of the rows of 12 consecutive real steps. Every GPU has one
38 GB/s port; hop latency 256 cycles (107 ns). Step time in µs.
`results_gem5_port_matrix.csv`, 112 runs.

**Sharded all-to-all (tables in GPU memory, the status quo)**

| Design | Step | Critical |
|---|---|---|
| One vector per lookup (TorchRec default for one-hot features) | 201.8 | 191.4 |
| Deduplicated per GPU | 44.6 | 34.6 |
| Deduplicated + sharing-aware sample placement | 33.7 | 24.3 |

**CXL pool (tables in the pool), by number of pool ports**

| Design | 1 port | 2 | 4 | 8 | Critical, 8 ports |
|---|---|---|---|---|---|
| Uncacheable, a reader combines gradients (**baseline**, CLAY for training) | 185.0 | 107.3 | 76.0 | 75.8 | 67.0 |
| + affinity sample placement | 116.3 | 63.0 | 41.5 | 41.4 | 32.8 |
| + software keeps private rows in the GPU | 94.8 | 51.8 | 34.6 | 34.5 | 26.7 |
| + commutative merge at the pool (scheduled sharing, software) | 82.0 | 42.5 | 25.6 | 25.6 | 17.8 |
| MESI, CXL-style (all transfers through the pool), affinity placement | 61.3 | 35.8 | 28.9 | 28.8 | 21.0 |
| **MESI + commutative updates, CXL-style (COUP), affinity placement** | 63.9 | 33.7 | 23.6 | **23.4** | **15.8** |
| MESI with GPU-to-GPU forwarding (not in CXL 3.0), affinity placement | 42.8 | 28.0 | 23.7 | 23.6 | 16.1 |

"Critical" = step time if rows that do not depend on the previous update are
prefetched during GPU compute. A pool with p ports has p x 38 GB/s to the
GPUs' switch.

## Findings
1. **Deduplication is the first fix for all-to-all: 4.5x.** Sending one
   vector per lookup costs 202 µs; one per (GPU,row) pair costs 45.
2. **A one-port pool loses to deduplicated sharding.** The best
   CXL-legal pool design takes 61-64 µs against 33.7 for sharding with the
   same placement. The pool needs more than 2 ports' worth of bandwidth to
   break even and gains nothing beyond 4.
3. **With 4 or more ports the pool is 1.3-1.44x faster than sharding with
   the same placement** (25.6 software, 23.4 hardware, vs 33.7), and 8.6x
   faster than per-lookup all-to-all. The whole gain comes from keeping a
   row at the GPU that alone uses it: without that the pool equals sharding
   (33.3 vs 33.7). Static shards cannot do this; the pool makes ownership
   dynamic.
4. **Commutative updates replace peer forwarding.** MESI plus a commutative
   update (a store to a line the GPU does not own is sent to the pool and
   merged) has no invalidations and no forwarding. It is 19% faster than
   CXL-style MESI at 8 ports and equals MESI with forwarding (23.4 vs 28.8
   vs 23.6). At one port forwarding still wins because it bypasses the port.
5. **Sample placement is the largest software lever in both architectures**:
   -25% for sharding (44.6 -> 33.7), -45% for the pool baseline (75.8 -> 41.4).
   Owner-aware placement for sharding was worse than sharing-aware placement
   (821K vs 740K transfers per step) and is not used.
6. **Placement is exact and its cost is measured.** Training with placed and
   with file-order batches gives the same model: after 40 steps the largest
   weight difference is 2e-14 and the AUC is identical (`placement_check.py`,
   float64). The placer in C (`placer.c`, same output as the Python one on
   all 32 steps) takes 22-50 ms per 65,536-sample step on one core.
7. **Sensitivity** (affinity placement, 8 ports for the pool):

   | Config | Sharded dedup | Pool, software | Pool, COUP |
   |---|---|---|---|
   | base | 33.7 | 25.6 | 23.4 |
   | GPU port 19 GB/s | 48.1 | 25.7 | 24.7 |
   | GPU port 154 GB/s | 29.1 | 25.5 | 23.1 |
   | hop 128 cycles | 25.5 | 15.3 | 15.2 |
   | hop 1024 cycles | 99.6 | 87.1 | 76.2 |

   Sharding is more sensitive to port bandwidth (a row crosses two GPU
   ports). Both are latency-bound at 32 outstanding requests.
8. **The ordering holds at 8x the trace scale** (1/8 row sample,
   `results_gem5_port_matrix_x8.csv`; step µs, 8 pool ports unless noted):
   sharded per lookup 1587.1, dedup 358.9, with placement 271.3; pool baseline 567.8 (1 port:
   1427.4); software scheduled sharing 195.3 (1 port: 637.2); CXL-style MESI
   207.4; MESI + commutative updates 172.0; MESI with forwarding 171.5. The
   pool's lead over sharding with the same placement is 1.39x (software)
   and 1.58x (MESI + commutative updates).
9. **One-step-stale reads cost no measurable accuracy** (`staleness_train.py`,
   28.6M Criteo samples): AUC 0.7346-0.7417 exact, 0.7379-0.7441 with 1-step
   delay, 0.7415-0.7459 with 4-step delay. With one step of staleness every
   fetch can be prefetched.
10. Traffic (`step_traffic.py`): a real step fetches ~297K (GPU,row) pairs
   over ~163K unique rows from 1.6M lookups; the top 1,000 rows are 73% of
   lookups but ~3% of deduplicated fetches.

## What this means for the project
- Against what Meta runs (per-lookup all-to-all), most of the gain is
  available without a pool: deduplicate (4.5x) and place samples (6.0x).
- A CXL pool adds 1.3-1.44x on top, only if it has several ports and only
  because rows can stay with the GPU that uses them. Its other benefit,
  capacity beyond GPU memory, is not evaluated here.
- For the pool, the coherence result is: MESI alone needs peer forwarding
  that CXL does not have; MESI plus commutative updates does not.

## Corrections to the first version
- **Port model.** SimpleNetwork limits bandwidth only on switch outputs, so
  in the default topology writes to the pool shared one 38 GB/s link while
  reads from the pool had one link per GPU. All runs now use an explicit
  topology (`--topology pool|sharded`, `--pool-ports`).
- **Gradient return was undercharged.** Uncacheable stores were emulated by
  lazy write-backs that overlapped the next reads. They are now real
  messages (`--commutative`: one data message up, one ack), issued in the
  gradient phase. The old headline (108.4 -> 48.7 µs, 2.2x) becomes
  185.0 -> 82.0 (2.3x) at one port and 75.8 -> 25.6 (3.0x) at 8 ports.
- **"CXL-style MESI ties software"** holds only at 4+ ports (28.8 vs 25.6).
  At 1-2 ports CXL-style MESI is faster than the software design (61.3 vs
  82.0): its 1 MiB cache retains more rows than the 4-step software window.
- **Pool-mediated MESI now covers reads too** (`--pool-mediated-gets`: the
  owner writes back and keeps a shared copy, as CXL BISnpData).
- Old numbers stay in `results_gem5_step_matrix.csv` for reference.

## Limits (read before quoting numbers)
- Per-lookup all-to-all is underestimated: the 1/64 row sample holds 58% of
  its share of lookups (hot rows are few), the 1/8 sample 67%.
- Local memory access is free in both architectures. The owner's work in
  sharding (lookup, gradient apply) and GPU compute are not simulated.
- The pool and the sharded system use the same link speed and hop latency;
  NVLink or RoCE against CXL is covered only by the sensitivity rows.
- Software keep uses a 4-step window; kept rows needing a store are charged
  a load (same count, opposite direction).
- The commutative merge needs an adder at the pool. The simulator does not
  track values, so the merge is timing only.
- Placement: one Criteo day, one-hot only. 22-50 ms per step has to be
  compared with a real step time, which was not measured.
- The staleness run is short (436 steps, small model).

## Novelty (honest)
Each mechanism has a precedent: Herald (NSDI'24) placement over RDMA
parameter servers; BagPipe (SOSP'23) and ScratchPipe (ISCA'22) lookahead
caches; COUP (MICRO'15) commutative coherence on multicores; ReCXL (ISCA'24)
and TrainingCXL do the embedding update inside CXL memory. Not found in
prior work: a timed comparison of a CXL pool against deduplicated sharded
all-to-all for the whole training step; the port-count break-even; and
commutative updates as the substitute for peer forwarding that CXL lacks.
